# Distribution, versioning & releases

How Frontier Commerce is versioned, released and consumed - and, just as
important, what each channel does **not** mean. The load-bearing principle
throughout: **sovereign deploy-your-own**. Nothing in this model creates a
shared canonical deployment; see "The deployment model" in the
[README](../README.md).

## The model at a glance

```
GitHub (Diabolacal/frontier-commerce)
  = the one canonical source + collaboration (issues/PRs)

GitHub tagged release  vX.Y.Z
  = a coherent, reviewed snapshot of EVERYTHING at one version:
    Move source, SDK source, gas station, indexer, deploy tooling, docs

npm  @frontier-commerce/sdk@X.Y.Z
  = the TypeScript SDK from that same tag, as a normal library dependency

deployments/<network>.json  (yours, generated by YOUR deploy)
  = your sovereign instance: your packageId/registry/merchant/caps,
    stamped with the source revision you published from

MVR (Move Registry)
  = NOT used to distribute this protocol (deliberate - see below)
```

One version number rides the whole train: git tag `v0.1.0` contains the
Move source of "Frontier Commerce 0.1.0" and builds
`@frontier-commerce/sdk@0.1.0`. There are no per-component version numbers
to cross-reference.

## What a consumer uses from each channel

| You want to... | Use |
|---|---|
| Call your deployed instance from an app (checkout, entitlements, events, sponsorship) | `npm install @frontier-commerce/sdk` (pin exact version) |
| Publish/upgrade your own sovereign instance | Clone the repo **at a release tag**, run the deploy tooling ([README quickstart](../README.md)) |
| Run the gas station / indexer / observability | Clone at the same tag - these are operated infrastructure, not libraries |
| Know what your deployment runs | Your descriptor's `evidence.source.revision` (written by `deploy-testnet.ts`) |
| Verify a deployed package matches released source | `sui client verify-source` against the tagged commit |

The SDK never hard-codes chain identity: it loads your descriptor at
runtime. Installing the npm package connects you to nobody's deployment.

## Versioning policy (pre-1.0)

- **Semantic-ish 0.x:** breaking changes bump the **minor** (0.1 → 0.2);
  fixes and compatible additions bump the **patch**. Nothing before 1.0
  promises stability, and 1.0 will not happen before the mainnet promotion
  checklist in [security-model.md](security-model.md).
- **One release train:** every workspace package carries the same version;
  only `@frontier-commerce/sdk` is published to npm. The others
  (gas-station, indexer, obs-collector, demo-consumer) are deploy-and-run
  infrastructure and stay `private` - publishing them would imply a
  library contract they don't have. (The indexer is the most plausible
  future candidate if demand appears.)
- **Move package versioning:** the Move source has no version field by
  design - source identity is the git tag; on-chain `version` is a
  per-instance fact of *your* deployment (fresh publish starts at 1, your
  upgrades increment it). "Which Frontier Commerce is deployed?" is
  answered by your descriptor's `evidence.source`, not by the chain.
- **Compatibility across the pair:** SDK `X.Y.*` is built for and tested
  against Move source `vX.Y.*`. Upgrade them together: adopt a new release
  tag, decide whether your instance needs the on-chain upgrade (see
  "Upgrading deliberately" below), and bump the SDK dependency in the same
  change.

## Release process (maintainers)

1. All gates green on `main` (CI: Move tests + TS build/typecheck/test).
2. Bump every workspace `version` together; update `CHANGELOG.md`.
3. Tag `vX.Y.Z` on the release commit; create a GitHub release whose notes
   state testnet/pre-mainnet status and the no-external-audit caveat.
4. Publishing the release triggers
   [`.github/workflows/release.yml`](../.github/workflows/release.yml),
   which re-runs the gates and publishes `@frontier-commerce/sdk` via
   **npm trusted publishing** (OIDC - tokenless, provenance attestations
   automatic). The tag must match the package version or the workflow
   fails.
5. npm versions are immutable: a bad release is fixed by publishing a
   patch, never by unpublish/republish.

One-time bootstrap (already-documented operator action): npm trusted
publishing cannot create a brand-new package, so the very first
`@frontier-commerce/sdk` version is published manually from a maintainer
terminal, after which the workflow is registered as the package's trusted
publisher and tokens are never used.

## MVR (Move Registry): what it is and why we don't distribute through it

[MVR](https://docs.suins.io/move-registry) maps a human-readable name
(`@namespace/package`) to a **specific registrant's published on-chain
package**. Its tooling resolves the name to that deployment's address (and
its pinned git source) so *other* Move packages and PTBs can build against
it; the resolver actively verifies the source matches the registered
on-chain package. Names are registered on **mainnet** (a SuiNS namespace +
mainnet transactions, even for testnet mappings), and unpinned PTB callers
follow whatever version the registrant's `UpgradeCap` holder publishes.

That is a great fit for protocols with one canonical deployment everyone
shares. It is **the opposite of this project's default**: an MVR name for
"frontier-commerce" would advertise *the authors' instance* as the thing
to depend on, and its consumers would be trusting the authors' upgrade
governance. Therefore, deliberately:

- **No MVR name is registered for Frontier Commerce today**, and no
  current testnet package ID is registered anywhere. Testnet IDs rotate
  (EVE Frontier cycles, our own re-publishes) and are evidence, not truth.
- **MVR is not how you obtain Frontier Commerce.** Source comes from
  GitHub release tags; the client library comes from npm.
- **Your own deployment is a legitimate MVR use case.** If *your* app
  wants other Move packages or PTB tooling to reference *your* instance by
  name (e.g. on-chain entitlement gating against your Merchant), you can
  register `@your-namespace/your-app-commerce` pointing at your deployment,
  under your own SuiNS namespace and your own governance. That is
  per-instance naming, exactly aligned with the sovereign model.
- **Revisited at mainnet promotion:** when the authors execute the mainnet
  checklist for their own instance, registering an MVR name *for that
  instance* (clearly named as the EF-Map deployment, not as "the"
  Frontier Commerce) will be evaluated then.

## Pinning and upgrading deliberately (consumers)

- **Pin the SDK exactly** (`"@frontier-commerce/sdk": "0.1.0"` - no `^`)
  while pre-1.0; your lockfile records the resolved integrity hash.
- **Record the tag you deployed from** - the deploy tool stamps
  `evidence.source` into your descriptor automatically.
- **To adopt a new release:** read its notes; upgrade the SDK dependency;
  if the Move source changed and you want it on-chain, either **upgrade**
  your instance (same `UpgradeCap`, same object IDs, `packageId` advances,
  `originalPackageId` stays) or **fresh-publish** a new instance (new
  everything - a migration, not an upgrade). Nothing upgrades implicitly;
  a new SDK version never mutates your chain state.
- **Source-level consumption still works.** Cloning or even submoduling
  the repo at a tag remains fine for people hacking on the platform
  itself - it just isn't the recommended way for an app to consume the
  SDK anymore. Apache-2.0 also permits forking and publishing under your
  own npm scope; keep the licence intact.
